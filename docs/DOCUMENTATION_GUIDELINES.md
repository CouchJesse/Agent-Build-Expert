# 开发项目文档管理规范

> 本文档为 `file-storage-compliance` 技能（统一权威，已合并原 `doc-management-standards`）的完整规范正文，供按需加载。项目内 `doc/DOCUMENTATION_GUIDELINES.md` 即本文件副本。

## 1. 文档存储机制

### 1.1 目录结构

```text
doc/                         # 正式文档交付区（六分类 + 管理元文档）
├── product/                 # 产品文档
├── development/             # 开发文档
├── technical/               # 技术文档
├── user/                    # 用户文档
├── deployment/              # 部署文档
├── test/                    # 测试文档
└── DOCUMENTATION_GUIDELINES.md  # 文档管理规范（元文档，固定文件名，不参与归档）
dev-work/                    # 开发工作区（日志/自测/临时），清理优先
config/                      # 配置区
├── dev/                     #   开发环境
├── test/                    #   测试环境
└── prod/                    #   生产环境
tools/                       # 脚本与通用工具
dochistory/                  # 历史文档归档（与 doc 平级，仅增不改）
```

> 业务文件禁止进入 `.workbuddy/` 等内部目录。

### 1.2 文档分类

| 目录 | 文档类型 | 包含内容 |
|------|----------|----------|
| product/ | 产品文档 | 产品需求、产品规划、产品设计等 |
| development/ | 开发文档 | 开发计划、开发规范、代码文档等 |
| technical/ | 技术文档 | 技术架构、技术方案、技术选型等 |
| user/ | 用户文档 | 用户手册、操作指南、FAQ 等 |
| deployment/ | 部署文档 | 部署指南、环境配置、升级方案等 |
| test/ | 测试文档 | 测试计划、测试用例、测试报告等 |

## 2. 文档版本控制

### 2.1 版本号格式

采用语义化版本号格式：`主版本号.次版本号.修订号`

- **主版本号**：文档结构或内容发生重大变化时递增
- **次版本号**：文档内容有较大更新但结构未变时递增
- **修订号**：文档内容有小的修正或补充时递增

### 2.2 版本标识

- 所有文档的版本号应在文档首页明确标识
- 文档命名中应包含版本号信息
- 历史文档应带有完整的版本标识

### 2.3 版本管理流程

1. **初始版本**：新文档创建时，版本号为 `1.0.0`
2. **内容更新**：根据更新程度递增相应的版本号
3. **历史归档**：文档更新后，旧版本应归档至 `dochistory` 目录

## 3. 历史文档归档系统

### 3.1 归档方式

- 历史文档应按时间顺序归档
- 每个版本的文档应保持完整的文件结构
- 归档文件应采用压缩格式存储，如 `.zip` 或 `.tar.gz`

### 3.2 归档命名规范

```text
dochistory/[文档类型]_[文件名序号]-[主题]_[创建日期]_v[主.次.修订].zip
```

示例：

```text
dochistory/product_01-用户增长方案_20240101_v1.0.0.zip
dochistory/test_03-某技能审计发现处理裁定记录_20260920_v1.0.0.zip
```

- **`[文件名序号]-[主题]` 为强制消歧段**。若归档名仅由 `[文档类型]_[创建日期]_[版本号]` 构成，则同一类型、同一创建日期、同一版本的多份不同文档必然同名（例如 `01-test_验收报告` 与 `03-test_裁定记录` 同属 `test` + `20260920` + `v1.0.0`），归档将互相覆盖或被迫追加无意义的数字后缀，且无法辨识归档归属哪份文档。
- `[文件名序号]`、`[主题]` 取自**归档时**该文档的文件名（与 `[NN]-[类型代码]_[主题]_[YYYYMMDD]_v[主.次.修订].md` 的对应字段一致）。
- 归档为**不可变历史快照**：其后若因 P0 清理阶段重排文件名序号，归档名**不随之改写**，以归档时的序号为准。
- 同一文档的同一版本被重复归档时，追加 `-2`、`-3` 序号，禁止覆盖已有归档。

### 3.3 归档周期

- 文档更新时应立即归档旧版本
- 定期对归档文档进行整理和清理

## 4. 文档命名规范

### 4.1 通用命名格式

```text
[NN]-[文档类型]_[主题]_[创建日期]_[版本号].md
```

- `NN`：2 位文件名序号（`01`、`02`…），清理阶段（P0）可重排。
- `[文档类型]`：`product` / `dev` / `tech` / `user` / `deploy` / `test`，须与所在 `doc/` 子目录一致。
- 业务文档编号（如 `BIZ-XXX-…`，前缀由项目自定义）写入文档首页 `文档编号` 字段，不进入文件名。

### 4.2 文档类型代码

| 类型 | 代码 | 示例 |
|------|------|------|
| 产品文档 | product | 01-product_requirements_20240101_v1.0.0.md |
| 开发文档 | dev | 01-dev_plan_20240101_v1.0.0.md |
| 技术文档 | tech | 01-tech_architecture_20240101_v1.0.0.md |
| 用户文档 | user | 01-user_manual_20240101_v1.0.0.md |
| 部署文档 | deploy | 01-deploy_guide_20240101_v1.0.0.md |
| 测试文档 | test | 01-test_plan_20240101_v1.0.0.md |

### 4.3 日期格式

采用 `YYYYMMDD` 格式，例如：`20240101`

### 4.4 示例

- 产品需求文档：`01-product_requirements_20240101_v1.0.0.md`
- 技术架构文档：`01-tech_architecture_20240101_v1.0.0.md`
- 用户手册：`01-user_manual_20240101_v1.0.0.md`
- 部署指南：`01-deploy_guide_20240101_v1.0.0.md`
- 测试计划：`01-test_plan_20240101_v1.0.0.md`

## 5. 文档创建与更新流程

### 5.1 文档创建

1. 根据文档类型选择相应的目录
2. 按照命名规范创建文档文件
3. 在文档首页添加文档信息（标题、版本号、创建日期、作者等）
4. 编写文档内容
5. 保存文档

### 5.2 文档更新

使用 `scripts/update_document.py` 升版时，必须按下列顺序执行：

1. 运行升版脚本——它先归档 `doc/` 下**当前磁盘文件**为旧版本，再递增版本号并写出新版本文件
2. 在**新版本文件**中修改正文，并核对首页版本号与更新日期
3. 确认 `dochistory/` 归档包完整（`ZipFile(...).testzip()` 返回 `None`）后，移除被取代的旧版本文件，保证 `doc/` 下仅留权威版

手工升版（无脚本环境）时同样遵循「先归档旧版、再写新版本」的顺序。

> ⚠️ **顺序陷阱**：升版脚本归档的是磁盘当前文件，且不修改正文。若先改正文再升版，归档包会捕获已修改内容，旧版本将无法回溯。

### 5.3 文档审核

- 重要文档应经过审核后发布
- 审核流程应在文档中明确记录
- 审核意见应作为文档的一部分保存

## 6. 文档管理工具

### 6.1 推荐工具

- **文档编辑**：Markdown 编辑器（如 VS Code、Typora 等）
- **版本控制**：Git（用于代码和文档的版本控制）
- **归档工具**：压缩软件（如 WinRAR、7-Zip 等）

### 6.2 工具使用规范

- 所有文档应使用 Markdown 格式编写
- 文档应纳入版本控制系统
- 归档文件应定期备份

## 7. 文档安全

### 7.1 访问控制

- 根据文档类型设置适当的访问权限
- 敏感文档应进行加密存储
- 文档共享应遵循最小权限原则

### 7.2 备份策略

- 定期备份文档目录
- 重要文档应多份存储
- 备份文件应定期验证

## 8. 附则

### 8.1 规范适用范围

本规范适用于本开发项目所有文档管理活动。

### 8.2 规范更新

本规范应根据项目需求和文档管理实践不断更新和完善。

### 8.3 解释权

本规范的最终解释权归项目团队所有。

## 9. 豁免登记

天然为 HTML / 其他格式的交付物（如交互原型、由脚本重建的生成物）可不补 `.md` 主版本，但必须逐条登记文件与理由（对应合规清理 P2 项）。

| 文件 | 类型 | 豁免理由 | 登记日期 |
|---|---|---|---|
| `<文件路径>` | 交互原型 / 生成产物 / 存量静态资产 | `<不补 .md 主版本的理由；若口径已由某文档承载，在此指明>` | `YYYY-MM-DD` |
