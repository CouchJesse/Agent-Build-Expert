## 2. 技能定位（三位一体）

技能以「产出可运行代码骨架」为主干，同时承担「指导构建」与「评审修正」两类职责。调用链路为：

```
选型决策 → 模式讲解 → 生成代码（新建场景）
   │
   └──→ 评审体检 → 定位根因 → 分级修正 → 验证闭环（评审场景）
```

结构化参数「任务类型」扩展为 5 类：

| 任务类型 | 含义 | 输出 |
|---|---|---|
| 构建指导 | 从零设计 Agent 应用 | 设计要点 + 模式选型 + 架构方案 |
| 评审审核 | 对已有 Agent 应用体检 | 体检清单 + 问题清单 + 修正步骤 |
| 模式选型 | 就单一决策点选模式 | 决策树 + 推荐 + 理由 |
| 生成代码 | 生成可运行骨架 | 多框架代码模板 + 工程骨架 |
| 讲解模式 | 讲解单个模式 | 定义 / 场景 / 要点 / 坑点 |

## 3. 核心能力模块一：构建指导（从零新建）

### 3.1 可操作原则（8 条）

> 每条原则均溯源至原书章节，供回溯原文。

**P1 · 目标与边界先行**（第 11 章 目标设定与监控）
先定义目标、成功标准、失败条件与越界清单，再谈模式选型。无明确目标的 Agent 必然发生目标漂移。

**P2 · 按复杂度选模式，拒绝过度设计**（第 2 章 路由 · 结论「组合模式」）
能用单步就不链式（第 1 章），能线性就不并行（第 3 章），能单 Agent 就不多 Agent（第 7 章）。模式复杂度必须与任务复杂度匹配。

**P3 · 提示即章程**（附录 A · FAQ「优质系统提示的关键组成」）
系统提示必须含六要素：角色与目标、工具定义、约束与规则、流程指令、示例轨迹、输出格式。

**P4 · 记忆三层分离**（第 8 章 记忆管理）
Session（会话跟踪）/ State（临时记事本）/ Memory（长期知识）职责清晰、不混用；长期知识不得污染会话上下文。

**P5 · 先反思后交付**（第 4 章 反思）
输出必经「检查你的工作」或「内部批评者」环节，与事实锚定（第 14 章 RAG）配合降低幻觉。

**P6 · 高风险必有人把关**（第 13 章 HITL · 第 18 章 护栏与安全）
删除、外发、交易、付费等操作必须人类审批；护栏前置而非事后补救。

**P7 · 失败要出声、可追溯**（第 12 章 异常处理 · 第 19 章 评估监控）
错误显式处理（重试 / 换工具 / 求助），全程留轨迹，结果可评估、可回溯。

**P8 · 组合显式声明取舍**（结论「组合模式构建复杂系统」· 第 20 章 优先级排序）
多模式协作要讲清「为何这样组合」，暴露而非掩盖权衡；按优先级收敛范围。

### 3.2 构建阶段设计检查项（10 项）

| # | 检查项 | 溯源 |
|---|---|---|
| 1 | 是否明确目标、成功标准、失败条件、边界？ | 第 11 章 |
| 2 | 复杂任务是否用 Planning / Prompt Chaining 拆解为可执行步骤？ | 第 6 / 1 章 |
| 3 | 所选模式是否与任务复杂度匹配、无过度设计？ | 第 2 章 |
| 4 | 工具是否有清晰功能描述、参数要求、错误处理？ | 第 5 章 |
| 5 | 系统提示是否含六要素？ | 附录 A |
| 6 | 记忆三层是否齐备、职责清晰？ | 第 8 章 |
| 7 | 高风险操作是否有 HITL 审批 + 输出过滤？ | 第 13 / 18 章 |
| 8 | 工具失败 / 超时是否有重试 / 换工具 / 求助策略？ | 第 12 章 |
| 9 | 是否定义结果导向 + 过程导向的评估指标？ | 第 19 章 |
| 10 | 是否记录完整智能体轨迹供调试？ | 第 19 章 |

### 3.3 示例场景

**场景 A · 客户咨询智能体（从零新建）**
- 需求：管理客户咨询，感知问题、访问知识库、与订单系统交互、主动澄清。
- 原则应用：先按 P1 定目标与边界（退款 / 投诉等敏感操作须审批）；再按 P2 选模式。
- 模式组合：`Planning`（拆解咨询流程）+ `Tool Use`（接知识库 / 订单 API）+ `RAG`（事实锚定）+ `HITL`（敏感操作审批）+ `Memory`（记住客户上下文）+ `Reflection`（降幻觉）。
- 决策说明：咨询流程多步骤有依赖，单 prompt 易丢目标，故引入 Planning 而非单次提示。

## 4. 核心能力模块二：评审修正（已有应用审核）

### 4.1 评审修正 SOP（5 步）

1. **摸底**：通读应用代码 / 提示 / 配置，识别其已用模式与整体架构。
2. **对照体检**：按 4.2 检查表逐项核对，标记「缺失 / 误用 / 过度设计」。
3. **定位根因**：将问题定位到具体环节（提示 / 工具 / 记忆 / 护栏 / 异常）。
4. **分级修正**：按风险与收益排序——P0 安全与正确性 → P1 效率与质量 → P2 优化。
5. **验证闭环**：按评估指标 + 轨迹验证，输出评审报告（问题 / 根因 / 修正 / 验证结果）。

### 4.2 评审阶段审核检查项（10 项）

| # | 检查项 | 溯源 |
|---|---|---|
| 1 | 行为是否偏离原始目标（目标漂移）？ | 第 11 章 |
| 2 | 是否模式误用（该用 Planning 却硬编码、该用 Routing 却全塞单 prompt）？ | 第 2 / 6 章 |
| 3 | 提示是否含糊、冗余、缺约束、缺示例？ | 附录 A |
| 4 | 是否缺 Reflection / RAG 事实锚定导致幻觉？ | 第 4 / 14 章 |
| 5 | Session / Memory 是否混用，长期知识污染会话？ | 第 8 章 |
| 6 | 工具权限控制缺失，错误被静默吞掉？ | 第 5 / 18 章 |
| 7 | 敏感操作是否未经审批自动执行？ | 第 13 / 18 章 |
| 8 | 单点失败是否导致流程整体崩溃？ | 第 12 章 |
| 9 | 是否过度内联导致上下文浪费？ | 第 16 章 |
| 10 | 是否无轨迹日志、无评估指标、失败无法定位？ | 第 19 章 |

### 4.3 示例场景

**场景 B · 客服机器人答非所问 + 幻觉（评审修正）**
- 症状：频繁编造不存在的产品信息，上下文错乱。
- 体检发现：① 无 RAG 事实锚定 → 幻觉；② 无 Reflection → 错误未纠；③ Memory 三层混用 → 上下文污染。
- 修正：加 RAG 检索 + 内部批评者反思 + 重构三层记忆。
- 验证：结果导向（答对率）+ 轨迹审查（是否走 RAG 链路）。

**场景 C · 多步骤数据处理 Agent 中途崩溃（评审修正）**
- 症状：处理到第 4 步失败即整体崩溃，无日志无法定位。
- 体检发现：① 无异常处理与恢复 → 单点失败崩溃；② 无轨迹记录 → 不可追溯；③ 无 State 持久化 → 无法断点续跑。
- 修正：加重试 / 换工具 / 求助策略 + 轨迹记录 + State 断点续跑。
- 验证：注入故障用例，确认能恢复或显式失败，而非静默崩溃。
