# 附录 A · 高级提示工程（Prompt Engineering）

> 溯源：《智能体设计模式》附录 A 高级提示工程技术 · 类型：附录参考
> 证据基准：除特别标注外，均为书中附录 A 原文确认 [F]；标注 [E] 为编者补充。

## 1. 定位

提示是与语言模型交互的主要接口，涵盖结构化请求、提供上下文、指定输出格式、展示期望响应类型 [F]。提示工程的目标是**持续获得高质量响应**，要求理解模型能力与局限并有效传达意图；这些技术适用于从聊天机器人到多智能体系统的全谱系——智能体模式的效能均依赖与模型的高质量交互 [F]。

## 2. 核心提示原则

| 原则 | 要点 [F] |
|---|---|
| 清晰与具体 | 模型依赖模式识别，歧义导致意外响应；明确任务、输出格式与限制条件 |
| 简洁 | 冗余复杂句式干扰理解；用直接表达与主动动词（Act、Analyze、Classify、Summarize…） |
| 动词使用 | "Summarize the following text" 优于 "Think about summarizing this"；精准动词激活相关训练数据 |
| 正面指令优于约束 | 明确期望行为优于强调不希望的行为；约束适用于安全或格式要求，过度依赖让模型聚焦规避 |
| 实验与迭代 | 起草→测试→分析→优化；记录尝试过程，持续迭代是必经之路 |

## 3. 基础提示技术（示例引导）

| 技术 | 示例数 | 适用场景 [F] |
|---|---|---|
| 零样本（Zero-Shot） | 0 | 训练中常见的任务：简单问答、文本补全、基础摘要 |
| 单样本（One-Shot） | 1 | 期望输出结构或风格较特殊 |
| 少样本（Few-Shot） | 3–5 | 特定格式/风格/细微变化：分类、结构化抽取、风格生成 |

示例设计要点 [F]：示例需准确、具代表性并覆盖边界情况（错误示例会误导模型）；分类任务建议混合不同类别的示例顺序，避免过拟合特定序列；长上下文模型支持「多样本」学习。

## 4. 提示结构与上下文工程

| 手法 | 机制 [F] |
|---|---|
| 系统提示（System Prompting） | 设定整体行为与交互目的，定义规则、角色或风格；可用于安全与毒性控制 |
| 角色提示（Role Prompting） | 为模型分配特定身份（如「资深数据分析师」），采用该角色的知识与语气 |
| 分隔符使用 | 用三重反引号、XML 标签或标记区分指令/上下文/示例/输入，减少误解 |
| 上下文工程（Context Engineering） | 区别于静态系统提示，**动态**提供背景：历史对话、检索文档（RAG）、工具输出、隐式数据（用户身份、交互历史、环境状态） |

上下文工程的核心论断 [F]：输出质量更多依赖**上下文丰富度**而非模型架构；它将无状态聊天机器人转变为情境感知系统，是记忆持久化与多任务协作的核心。隐式上下文集成需注意隐私与伦理治理 [F]。

## 5. 结构化输出

明确要求输出格式（JSON、XML、CSV、Markdown 表格）并提供示例或 Schema；请求 JSON 有助于**限制幻觉**、便于数据抽取与管道集成 [F]。

面向对象封装（Pydantic）[F]：定义继承 BaseModel 的数据模型（字段以类型注解加 Field 描述声明）；LLM 输出的 JSON 用 model_validate_json 一步完成解析与校验，ValidationError 捕获格式错误；XML 可先经 xmltodict 转字典再解析。意义：输出封装为对象后可安全传递给函数、API 或数据管道 [E]。

## 6. 推理与思考过程技术

| 技术 | 机制 | 要点与成本 [F] |
|---|---|---|
| 思维链（CoT） | 生成中间推理步骤（「一步一步思考」） | 零样本 CoT 仅加一句指令；少样本 CoT 提供含推理过程的示例。无需微调、可解释性强，但 Token 消耗增加。答案置于推理后；单一答案任务温度设 0 |
| 自洽性（Self-Consistency） | 较高温度生成多条推理路径→多数投票 | 提升准确性与一致性；需多次运行，成本高 |
| 反思提示（Step-Back） | 先考虑通用原则，再解决具体问题 | 激活背景知识、提升推理深度 |
| 思维树（ToT） | 并行探索多条推理路径，节点可分支与回溯 | 适合探索、回溯、多方案评估类问题；计算量大 |

## 7. 行动与交互技术

- **工具使用 / 函数调用** [F]：现代模型针对函数调用微调。模型本身**不执行**工具，而是生成结构化输出（如 JSON，含工具名与参数），由智能体系统执行并回传结果。有效提示需设计何时、如何使用工具。
- **ReAct** [F]：结合 CoT 推理与工具使用，循环「思考→行动→观察」直至输出最终答案，适合与动态环境或外部知识交互的任务。

书中定位 [F]：ReAct 与函数调用是智能体的「手」；RAG 与上下文工程是智能体的「感官」——主动检索实时知识，摆脱静态训练数据局限。

## 8. 高级技术

| 技术 | 机制 [F] |
|---|---|
| 自动提示工程（APE） | 用「元模型」生成候选提示，按输出质量（BLEU、ROUGE 或人工评估）筛选。程序化框架（如 DSPy）将提示视为可优化模块：Goldset 数据集 + 目标函数，优化器执行少样本示例优化与指令优化 |
| 迭代提示 / 精炼 | 从简单提示开始，按初始响应的不足逐步优化 |
| 负面示例 | 「正面指令优于约束」的例外：明确边界或防止错误输出 |
| 类比使用 | 用类比帮助模型理解任务（如「数据厨师」用数据点烹制报告） |
| 分解认知 / 任务拆分 | 复杂任务拆为子任务分别提示再合并——类似提示链与规划 |
| 检索增强生成（RAG） | 检索外部知识库增强上下文，减少幻觉、支持动态或专有信息 |
| 用户画像（Persona Pattern） | 区别于角色提示（给模型身份）：画像描述**目标受众**，调整语言、复杂度、语气 |
| 专用智能体实例 | 书中以 Gems 为例：以指令集定义用途、风格与知识领域的定制实例，建立持久任务专用上下文 |
| 元提示（元方法） | 用 LLM 优化提示：提供现有提示与输出不足，要求提出改进。优势：加速迭代、发现盲点；仍需人工评估 |

## 9. 特定任务提示

- **代码提示** [F]：四类场景——生成（按功能描述）、解释（逐行或总结）、翻译（跨语言）、调试与评审。要点：提供足够上下文、明确语言与版本、清楚描述问题。
- **多模态提示** [F]：多种输入格式组合（图片 + 文本），如输入流程图要求解释流程。

## 10. 最佳实践清单

| 类别 | 实践要点 [F] |
|---|---|
| 设计 | 提供示例（最有效的引导）；设计简洁；明确输出要求（格式、长度、风格）；优先正面指令；CoT 答案置于推理后、温度设 0 |
| 工程化 | 提示变量化（避免硬编码）；提示存独立文件便于版本控制；结构化记录提示与结果；生产系统需自动化测试与评估 |
| 迭代 | 尝试不同输入/输出格式（非创意任务尤甚）；分类示例顺序随机化；适应模型更新；协作实验 |
| 成本 | 控制最大 Token 长度（模型参数或提示指令）[E 汇总] |
