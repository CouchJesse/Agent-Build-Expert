# 12 · 智能体间通信（Agent-to-Agent，A2A）

> 溯源：《智能体设计模式》第 15 章 智能体间通信（A2A）· 板块：协作与通信
> 证据基准：本节内容除特别标注外，均为书中原文确认 [F]。

## 1. 模式定义

Agent-to-Agent（A2A）协议是一项开放标准，旨在实现不同智能体框架之间的通信与协作，确保互操作性——使基于 LangGraph、CrewAI 或 Google ADK 等不同技术开发的智能体能够跨平台协同工作 [F]。它解决的核心问题是：单个智能体面对复杂、多层次问题时力不从心，缺乏统一协议导致各自为政、集成成本高、难以组合专长解决更大任务 [F]。

远程智能体（A2A 服务器）作为「黑盒」系统对外提供服务：客户端只需了解其能力与端点，无需知晓内部实现细节 [F]。A2A 得到多家主流科技企业与服务商的支持，并作为开源协议鼓励社区贡献 [F]。

## 2. 工作机制

```text
用户 → A2A 客户端（客户端 Agent） --HTTP(S) + JSON-RPC 2.0--> A2A 服务器（远程 Agent，黑盒）

任务生命周期: 提交 → 处理中 → 完成 / 失败 / 需补充输入(input-required) [F]
上下文关联:   服务器生成 contextId，关联同一会话的多次任务 [F]
数据载体:     消息(message) = 元数据属性 + 多个内容部分(文本/文件/结构化 JSON)
             artifact(工件) = 任务的实际输出，与消息类似由多部分组成，可流式传输 [F]
```

核心概念 [F]：

- **三类参与者**：用户（发起智能体协助请求）、A2A 客户端（代表用户请求操作或信息的应用或 AI Agent）、A2A 服务器（提供 HTTP 端点处理请求并返回结果的智能体或系统）。
- **AgentCard**：智能体的数字身份（通常为 JSON 文件），包含身份、端点 URL、版本号、能力声明（流式传输/推送通知）、技能清单、默认输入/输出模式及认证要求——是自动发现与交互的基础。
- **Agent 发现（三种方式）**：Well-Known URI（在 /.well-known/agent.json 等标准路径托管卡片）；管理型注册表（集中式目录，适合企业环境的集中管理与访问控制）；直接配置（嵌入或私下共享，适合紧密耦合的私有系统）。
- **交互机制（四种）**：同步请求/响应（快速操作，一次性完整响应）；异步轮询（耗时任务，返回任务 ID 后定期查询）；流式更新（SSE，服务器到客户端的单向持久连接，持续推送状态或部分结果）；推送通知（Webhook，超长或资源密集型任务在状态显著变化时异步回调）。
- **安全性（内置机制）**：双向 TLS（mTLS）建立加密与认证连接；完整审计日志记录所有智能体间通信；认证要求在 AgentCard 中集中声明；凭证用 OAuth 2.0 令牌或 API Key，经 HTTP 头传递，避免暴露在 URL 或消息体中。

## 3. 适用场景与不适用场景

| 适用 ✅ | 不适用 ❌ |
|---|---|
| 多框架协作：不同框架构建的独立智能体跨平台通信协同 [F] | [E] 单智能体可完成的任务：协议接入开销无收益 |
| 自动化工作流编排：数据采集→分析→报告智能体间的任务委托 [F] | [E] 同一框架内的多智能体编排：用框架原生编排（见 10 多智能体）更直接 |
| 动态信息检索：主智能体向专门的数据获取智能体请求实时信息 [F] | [E] 紧密耦合的进程内模块通信：直接函数调用延迟更低 |
| 需动态发现并调用其他智能体能力的开放生态 [F] | |

书中使用原则 [F]：需要编排两个或以上智能体协作，尤其跨框架时，建议采用此模式；各智能体专注于工作流不同环节（如分析委托一个、报告生成交由另一个）、需动态发现和调用其他智能体能力时也适用。

## 4. 选型决策要点

**A2A 与 MCP 对比**（书中重要内容：二者互为补充 [F]）：

| 维度 | MCP（11） | A2A（12） |
|---|---|---|
| 关注点 | 智能体与外部数据和工具的上下文结构化 | 智能体间的协调与通信，实现任务委托与协作 |
| 定位 | 为 LLM 与外部资源交互提供标准接口 | 智能体间任务和工作流管理 [F] |
| 通信对象 | 工具、数据源、应用 [E] | 智能体（远程 Agent，黑盒）[E] |
| 发现机制 | 客户端查询服务器能力（工具/资源/Prompt 清单）[E] | AgentCard 数字身份 + Well-Known URI/注册表/直接配置 [E] |
| 任务模型 | 工具调用，请求-响应为主 [E] | 异步任务生命周期（提交/处理中/完成/input-required）[E] |
| 组合关系 | 互为补充：MCP 接工具与数据，A2A 委托任务，常配合使用 [F] | |

1. **先分清「连工具」还是「连智能体」** [F]：让智能体访问外部数据与工具 → MCP；让智能体把任务委托给另一个智能体 → A2A。二者不是竞争关系而是互补。
2. **跨框架是最大信号** [F]：协作双方来自不同框架（如 ADK、LangGraph、CrewAI）时，A2A 是标准化的互操作通道。
3. **按任务特征选交互机制** [F]：快速操作 → 同步请求/响应；耗时任务 → 异步轮询；实时增量结果 → SSE 流式；超长资源密集任务 → Webhook 推送。
4. **安全前置** [F]：AgentCard 端点须以访问控制、双向 TLS（mTLS）或网络限制保护，尤其当卡片包含敏感（虽非密钥）信息时；认证要求在卡片中声明，凭证经 HTTP 头传递。
5. **模块化收益评估** [F]：A2A 鼓励模块化架构——专用智能体可独立运行于不同端口，实现可扩展与分布式部署；是否值得为此付出协议化成本由系统规模决定 [E]。

## 5. 多框架代码模板

### 5.1 框架无关伪代码

```text
# A2A 服务器侧（远程 Agent）
agent_card = AgentCard(
    name="my_weather_agent", url="http://my-service.example.com/a2a",
    capabilities={streaming: true},
    skills=[{id, description, input_modes, output_modes}],   # 技能清单
    authentication={schemes: ["apiKey"]})                     # 数字身份，供发现
server = A2AServer(card=agent_card, handler=MyAgentExecutor())

# A2A 客户端侧（客户端 Agent）
card  = discover("http://my-service.example.com/.well-known/agent.json")  # 发现
task  = client.sendTask(card.url, message=用户请求, auth=凭证)            # 委托任务
while task.status in {submitted, working}:      # 异步任务生命周期
    task = poll_or_stream(task.id)              # 轮询 / SSE 流式 / Webhook 推送
result = task.artifacts                         # 消费工件
```

## 6. 反模式与坑点

1. **协议错位** [F]：用 A2A 去接外部工具/数据，或用 MCP 去做智能体间任务委托。正确分工：MCP 关注智能体与外部数据和工具的上下文结构化，A2A 专注于智能体间的协调与通信。
2. **AgentCard 端点裸奔** [F]：卡片包含敏感（虽非密钥）信息，须通过访问控制、双向 TLS 或网络限制保障端点安全。
3. **凭证暴露在 URL 或消息体** [F]：应通过 HTTP 头传递 OAuth 2.0 令牌或 API Key。
4. **[E] 长任务强制同步等待**：耗时任务应选异步轮询、SSE 流式或 Webhook 推送，且 AgentCard 须如实声明是否支持流式/推送能力。
5. **忽视 input-required 多轮机制** [F]：A2A 支持多轮对话，Agent 可请求补充信息并保持上下文；信息不足时应请求补充，而非硬猜。
6. **单体倾向** [F]：把所有能力塞进一个智能体。A2A 鼓励模块化——专用智能体独立运行于不同端口，实现可扩展与分布式部署。

## 7. 与其他模式的组合

- **A2A + 多智能体（10）**：A2A 是多智能体协作在跨框架场景下的标准化通信层——任务委托与信息交换经 A2A 协议完成 [F]。
- **A2A + MCP（11）**：互补组合——每个远程智能体内部用 MCP 连接工具与数据，智能体之间用 A2A 委托任务 [F]。
- **A2A + 规划（04）**：工作流编排中，规划者拆解任务后经 A2A 委托给各专职智能体（数据采集→分析→报告）[F]。
- **A2A + HITL（15）**：input-required 状态下智能体向用户请求补充信息并保持上下文，是协议内置的人机交互挂点 [F]。
- **A2A + 异常恢复（14）** [E]：任务失败状态与通知机制支撑跨智能体的故障告警与升级处理。
- **A2A + 评估（19）**：可视化与跟踪工具可监控、调试和优化 A2A 通信，为多智能体系统提供通信级观测 [F]。

## 8. 评估指标

- **结果导向**：任务委托成功率（客户端发起→服务器完成）；跨框架任务端到端完成率 [E]。
- **过程导向**：任务生命周期耗时（提交→处理中→完成的各阶段延迟）；交互机制适配率（按任务特征选对同步/轮询/流式/推送的比率）；AgentCard 发现与解析成功率 [E]。
- **架构导向**：模块化收益（智能体独立部署与复用次数）；审计日志完整度——完整审计日志应记录所有智能体间通信（信息流、参与智能体和操作）[F]。
